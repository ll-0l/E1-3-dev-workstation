## 2. 항목별 예상 질문과 답변

### 1. 모드 1 사용자 입력
**Q. 모드 1의 흐름을 설명해 주세요.**
`run_user_mode()`는 다음 순서로 진행돼요.
1. `read_matrix()`로 필터 A와 B를 3줄씩 받아요.
2. 저장한 값을 `Matrix.format()`으로 다시 출력해서 제대로 저장됐는지 보여 줘요.
3. 패턴을 받아요.
4. `report_ab_judgement()`가 MAC 2번(A, B), 시간 측정(10회 평균), `judge()` 판정을 해요.
5. 마지막으로 3×3 성능표를 출력해요.

과제 예시를 입력하면 `A 점수: 1.0 / B 점수: 5.0 / 판정: B`가 나와요.

### 2. epsilon 정책
**Q. 왜 1e-9인가요?**
- data.json의 오차는 1.1e-16 ~ 2.7e-15이고, 진짜 점수 차이는 0.1 이상이에요. 1e-9는 이 둘 사이에 넉넉하게 들어가요.
- 실험해 보니 1e-12 ~ 1 사이의 어떤 값을 넣어도 결과가 같았어요. 1e-15 이하로는 오차를 걸러내지 못했고, 10은 진짜 차이까지 동점으로 삼켰어요(README 4-2 표).
- 이 근거는 코드 주석(L35~37)에도 적어 뒀어요.

### 3. 입력 검증
**Q. 잘못 입력하면 어떻게 되나요?**
`parse_row()`가 세 가지를 검사해요. 빈 줄(행 누락), 숫자 개수(열 수 불일치), 숫자 변환 실패(`float()`에서 나는 ValueError)예요. 추가로 `nan`과 `inf`도 거부해요.
오류가 나면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요. (이유)`를 출력하고, **그 줄만** 다시 받아요. 올바른 줄이 3개가 될 때까지 받기 때문에, 행 수가 틀리는 일은 구조적으로 생기지 않아요.

### 4. 필터 로드
**Q. filters 섹션은 어떻게 읽나요?**
`load_filters()`는 키마다 다음 순서로 처리해요.
1. `^size_(\d+)$`로 N을 뽑아요.
2. 하위 키(`cross`, `x`)를 정규화해요.
3. `Matrix.from_rows(rows, expected_size=N)`로 크기와 숫자를 검증해요.

실패해도 예외를 던지지 않아요. 대신 `FilterLoad.error`에 이유를 남겨요. 그 크기의 패턴은 "필터를 사용할 수 없습니다 (이유)"로 FAIL 처리돼요.

### 5. 라벨 정규화 구현
**Q. 정규화는 어디서 하나요?**
`normalize_label(raw)`는 `LABEL_ALIASES.get(raw.strip().lower())` 한 줄로 처리해요. expected 값과 필터 키 모두 이 함수를 거쳐요. 문자열이 아니거나 표에 없는 값이면 `None`을 돌려주고, 그 케이스는 스키마 FAIL이에요.

### 6. 판정과 PASS/FAIL
**Q. UNDECIDED는 왜 FAIL인가요?**
expected는 항상 Cross나 X 중 하나예요. 그래서 UNDECIDED는 정의상 expected와 같을 수 없어요. 출력은 `판정: UNDECIDED | expected: X | FAIL (동점 규칙)`처럼 나와요. 요약에서는 `[동점]` 분류로 따로 집계해요.

### 7. 성능 표
**Q. 시간은 어떻게 재고, 표에는 무엇이 있나요?**
크기마다 1번 예열한 다음, `measure_ms(mac, pattern, filt, repeat=10)`으로 평균을 내요. 표에는 크기, 평균 시간(ms), 연산 횟수(N²), N²당 시간(ns), 입력 출처가 있어요. 3×3은 data.json에 없어서 생성기 패턴을 써요.

### 8. 결과 요약
**Q. 실패 사유는 어떻게 보이나요?**
`print_summary()`가 다음을 출력해요.
- 총 테스트, 통과, 실패 개수
- `- 케이스ID: [분류] 사유` 목록
- `실패 원인 분류: 동점 3건`

분류는 `스키마` / `동점` / `판정 불일치` 세 가지예요. 각각 데이터 문제, 수치 비교 문제, 로직 또는 라벨 문제를 가리켜요.

### 9. README 결과 리포트
**Q. 리포트는 어디 있나요?**
README 4장 한 곳에 모았어요.
- 4-1: 실행 결과
- 4-2: FAIL 원인을 3단계로 분석, epsilon 민감도
- 4-3: O(N²), 이론과 측정 비교, NPU 관점
- 4-4: 요약
- 4-5: 대규모 N

### 10. MAC 원리
**Q. MAC이 뭔가요?**
같은 위치의 값끼리 곱하고(Multiply) 그 결과를 계속 더하는(Accumulate) 연산이에요. 수식으로는 `점수 = ΣΣ P[i][j] × F[i][j]`예요. `mac()`은 이중 반복문 안에서 `total += p_row[j] * f_row[j]`를 N²번 실행하고, float를 돌려줘요.

### 11. 키에서 N 추출
**Q. 패턴과 필터는 어떻게 연결하나요?**
`PATTERN_KEY_RE = ^size_(\d+)_(\d+)$`에서 첫 번째 그룹이 N이에요. 이 N으로 `filters[N]`을 찾아요. 그다음 input이 N×N인지 다시 확인해요. 예를 들어 키는 `size_5`인데 input이 4×4라면 "크기 불일치" FAIL이에요. 키 형식이 다르면(`cross_5_1`) "패턴 키 형식 오류" FAIL이에요. 여기에 쓰는 오류 데이터는 `tests/fixtures/bad_data.json`에 10가지가 있어요.

### 12. 라벨 정규화가 필요한 이유
**Q. 왜 정규화하나요?**
같은 뜻인데 표기가 세 가지예요. expected는 `+`/`x`, 필터 키는 `cross`/`x`, 출력은 `Cross`/`X`예요. 정규화하지 않으면 `"+" == "cross"`가 거짓이 돼서 맞는 판정도 FAIL이 나요. 입구에서 한 번 통일해 두면, 내부 로직은 두 값만 다루면 돼요. 표기가 늘어나도 별칭 표에 한 줄만 추가하면 돼요.

### 13. 시간 측정 범위
**Q. I/O 시간은 어떻게 뺐나요?**
`measure_ms()`는 `perf_counter()`로 `func(*args)` 호출만 감싸요. 파일 읽기, `print`, `input`은 측정 구간 밖에 있어요. 추가로 측정하는 동안에는 GC를 꺼서(`gc.disable()`) 메모리 정리 작업이 끼어들지 않게 했고, 첫 호출은 예열로 뺐어요.

### 14. 점수의 의미
**Q. 점수가 높으면 뭘 뜻하나요?**
패턴과 필터가 겹치는 칸이 많고 가중치가 클수록 점수가 높아요. 다만 필터마다 칸 수와 가중치가 달라서, "몇 점 이상이면 Cross" 같은 절대 기준은 쓸 수 없어요. 그래서 **같은 패턴에 대한 두 필터 점수를 서로 비교**해요.

### 15. O(N²)
**Q. 근거가 뭔가요?**
- **코드**: 이중 반복문이라 본문이 N²번 실행돼요.
- **측정**: 모델 `T = a + c·N²`(c ≈ 40ns)로 3×3부터 1000×1000까지 예측해 보면, 실제 측정값과 ±5% 안에서 맞아요. 또 N이 2배일 때(250→500→1000) 시간이 3.91배, 4.11배가 돼요.

### 16. 부동소수점
**Q. 실제로 오차가 문제가 됐나요?**
네. data.json의 FAIL 3건이 그 예예요. 분수로 정확히 계산하면 두 점수가 완전히 같은데, float로는 `0.9` vs `0.8999999999999999`처럼 달라져요. epsilon 없이 비교하면 세 건 모두 정답과 반대 라벨이 나와요.

### 17. 모드 1과 모드 2의 동점 처리 차이
**Q. 두 모드에서 동점은 어떻게 다르게 다뤄지나요?**
판정 함수(`judge`)와 기준(1e-9)은 같아요. 달라지는 건 출력과 집계예요.
- **모드 1**: 정답이 없어서 `판정: 판정 불가 (|A-B| < 1e-9)`만 보여 줘요.
- **모드 2**: `UNDECIDED`를 출력하고, expected와 비교해서 **FAIL(동점 규칙)** 로 집계해요.

README 3-4에 비교표가 있어요.

### 18. 새 라벨이 생기면
**Q. 라벨이 추가되면 어디를 고치나요?**
- **별칭만 추가할 때**: `LABEL_ALIASES`에 한 줄, 테스트에 한 줄만 추가하면 돼요.
- **새 모양(예: O)을 추가할 때**: 라벨 상수를 만들고, `load_filters`의 필수 라벨 검사와 `evaluate_case`의 비교 방식(두 필터 비교 → 1등과 2등 비교)을 바꿔야 해요.

체크리스트는 README 3-3에 있어요.

### 19. 대규모 N (보완 항목)
**Q. 1000×1000이면 어떻게 되나요?**
모드 5로 직접 측정했어요. MAC 1회는 41.6ms, 행렬 1개는 32.9MB였어요. 문제는 세 가지였고, 각각 이렇게 대응했어요.

| 문제 | 측정값 | 대응 | 효과 |
|---|---|---|---|
| ① 정밀도 | 0.1을 100만 번 더하면 오차 1.3e-6 | 상대 허용오차 `REL_EPSILON`(옵션) | 250×250부터 고정 1e-9가 놓치던 진짜 동점을 잡아요 |
| ② 시간 | 일반 MAC 41.6ms | 희소 MAC `mac_sparse`(0이 아닌 칸만 계산) | 130배 빨라지고, 결과는 비트 단위까지 같아요 |
| ③ 입력 검증 | 288ms (MAC보다 느렸음) | 행 단위 빠른 경로 | 84ms로 줄었어요 |

메모리는 `array('d')`를 쓰면 4배 절약된다는 것까지 측정했어요. 병렬화와 스트리밍은 우선순위를 정해서 설계까지만 했어요(README 4-5).

### 20. CPU와 NPU의 차이와 병목
**Q. 왜 NPU가 필요한가요?**
CPU는 곱셈 1번마다 값을 읽고, 곱하고, 더하고, 다음 칸으로 넘어가는 일을 차례로 반복해요. N²에 비례해서 느려지고, 이 프로그램 기준으로 25×25 MAC 1억 번이면 약 45분이 걸려요.

NPU는 병목 두 가지를 다르게 풀어요.
- **연산 병목**: 독립적인 곱셈을 수천 개씩 동시에 처리해요.
- **메모리 병목**: 가중치를 칩 안의 가까운 메모리(SRAM)에 두고 재사용하고, 결과를 옆 계산기로 바로 넘겨요(systolic array). 느린 외부 메모리 접근을 줄이는 거예요.
